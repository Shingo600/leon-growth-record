# おでかけAIアドオン 実装計画

作成日: 2026-09-28
更新日: 2026-09-29
状態: UI画像を先に作成し、アプリ実装済み。外部サービス設定・実API検証・公開は未実施。
導入手順: [outings-addon-setup.md](./outings-addon-setup.md)。

## 必須の進め方

先にimagegenでUIイメージ画像を作成し、その画像を実装のデザイン基準とする。
最初にスマホ版の「探す / 行きたい」のイメージを作り、PCは同じカードと余白のルールで展開する。
画像の施設は架空のサンプルと明記する。生成画像の文字や数値は本番データとして使用しない。
画像作成後に画面コードを実装し、実際のブラウザ表示を画像と比較して調整する。

初稿: [UIイメージ v1](./outings-addon-ui-v1.png)。左が「探す」、右が「行きたい」。
生成方法: 内蔵imagegen。プロンプトは [outings-addon-ui-prompt.md](./outings-addon-ui-prompt.md) に保存。
画像はデザイン参照用。実装では本文の仕様を優先し、検索日時・出典・横スクロール可能な全9タブ・選択状態を正確に反映する。

## 目的と範囲

新しいアプリ内タブ「おでかけ」から、地域と条件に合う犬とのお出かけ先をAIで検索し、出典サイトを開けるようにする。
addonは既存アプリに組み込む独立機能を指す。ブラウザ拡張や汎用プラグイン基盤は作らない。
AI以外に有料サービスを追加しない。既存Vercel・Supabaseの無料枠内での運用を前提とする。

## 初回リリース

- 新規ルート `/outings` と「おでかけ」ナビ項目。
- ページ内の「探す / 行きたい」切替。
- 地域名、施設ジャンル、希望条件、自由文で検索。
- 実際のWeb検索に基づく候補を最大5件表示。少ない場合に架空の候補で埋めない。
- 施設名、地域、おすすめ理由、犬同伴条件、情報源リンク、検索日時を表示。
- 「サイトを見る」「行きたいに保存」「保存から外す」。削除はお気に入りの解除のみ。
- API未設定、未認証、検索中、0件、通信失敗、利用上限、オフラインの画面。

初回は手入力の地域検索を優先する。現在地、地図埋め込み、車の所要時間、写真取得、予約、訪問記録、予定追加は後続拡張。
営業時間や料金は出典から取得できた場合のみ参考情報として表示し、「現在営業中」などの保証はしない。

## 画面と操作

### 確定したジャンル

ユーザー確認済み: 「すべて」+ 以下の6ジャンル。

| ジャンル | 対象 |
|---|---|
| ドッグラン | 屋外・屋内のドッグラン |
| 公園・散歩 | 犬と歩ける公園、遊歩道、広場 |
| カフェ・飲食店 | 犬同伴可能なカフェ、レストラン |
| 自然・アウトドア | 海、川、山、ハイキング、キャンプ場 |
| 観光・おでかけ | 犬同伴可能な観光施設、牧場、道の駅 |
| 宿泊 | 犬と泊まれるホテル、旅館、コテージ |

初期選択は「すべて」。ジャンルは単一選択、条件は複数選択とする。
「大型犬OK / 屋内 / 駐車場あり / 無料 / 貸切」はジャンルから分離した条件チップとして扱う。
無料は施設利用料についての条件とし、駐車料金などは別途確認事項として表示する。
ジャンルや地域が合っても犬同伴可とは推測しない。条件未確認は「要確認」とする。
UI画像v1のジャンルは簡略表示。実装は上記の確定仕様に合わせ、チップを複数行に折り返して押しやすさを保つ。

### 操作の流れ

1. 「おでかけ」タブを開く。開いただけではAIを呼び出さない。
2. 地域を入力し、「すべて」または確定した6ジャンルから選ぶ。
3. 「大型犬」「駐車場」「屋内」など希望条件を選ぶ。条件は必須条件として扱い、不明な候補は別の「条件要確認」枠に分ける。
4. 「AIで探す」を押す。検索中は多重送信を防ぐ。
5. カードから参照サイトを別タブで開く、またはお気に入りに保存する。
6. 「行きたい」から保存した場所を再確認する。ここではAIを呼ばない。

検索後に条件を変更しても自動再検索しない。結果には検索時の条件を残し、新条件の結果と取り違えないようにする。
保存済みカードには保存日と元の検索日を表示し、最新情報だと誤認させない。
現在のカード・色・文字サイズのルールに合わせ、操作領域は44px以上を目安とする。
既存ナビは8項目。9項目を狭く均等配置せず、スマホ下部とPC上部は横スクロール対応とし、選択中タブを見える位置にする。PCサイドバーも高さに応じてスクロール可能にする。

## AI検索とURLの扱い

採用: OpenAI Responses APIのWeb検索。初期モデルは `gpt-4.1-mini`。サーバー設定で変更できる。
計画時のGemini候補から、結果を独自カードに整形して保存する用途に合わせて変更した。
プロバイダー呼び出しは `lib/addons/outings/provider.ts` に閉じ込め、画面は共通の検索結果型だけを利用する。

- AI検索が返す引用・出典情報と各施設の説明を対応付ける。
- モデルが本文やJSONに書いただけのURLは採用せず、出典に対応するURLだけを表示する。
- 出典がない、施設との対応が曖昧、回答形式が壊れている場合は候補として確定しない。
- 出典URLがあるだけで公式サイトとは断定しない。確認できた場合に「公式サイト」、その他は「紹介サイト」または「参照サイト」と表示。
- URLはhttp/httpsのみ許可し、認証情報付きURLやローカル宛先は拒否。外部リンクに `noopener noreferrer` を付ける。
- URLのHTTP成功だけで施設情報の正しさは確認できないため、汎用のサーバー側URL取得機能は追加しない。
- 検索資料中の指示はデータとして扱い、アプリの指示・認証・保存処理には使わない。
- 出典、検索候補、保存可能範囲など、採用サービスの表示・保存規約を実装前に確認する。
- 永続保存は施設名・出典URL・ユーザーメモ・日時などを基本とする。生成本文の保存は規約確認後に判断。

## 独立性・認証・費用制御

- `/outings` とその配下のAPI・コンポーネントで完結する。AIコードを共通画面の初期読み込みに含めない。
- `OUTINGS_ADDON_ENABLED` でサーバー側停止が可能。停止・未設定時は説明を表示し、AI通信は行わない。
- `OPENAI_API_KEY` とモデル設定はサーバーだけで参照し、公開環境変数やブラウザ入力欄に置かない。
- 既存の同期コードによる認証Cookieを再利用し、検索・共有保存APIで必ず検証する。未認証時は入力導線を表示する。
- AIに送るのは地域、条件、希望文など検索に必要な項目のみ。成長記録・写真・家族の記録一式は送らない。
- 有料のPlaces API、経路API、別契約の検索APIは追加しない。
- AI内蔵検索のツール料金も費用に含む。生成料金だけで検索できるとは説明しない。
- 暫定で家族全体1日10回、結果最大5件、入力文字数・出力・実行時間の上限を設ける。値は設定化する。
- 回数制限はサーバーメモリやlocalStorageではなく、Supabaseの小さな専用カウンターと原子的な更新で判定。JSTの日付で管理する。
- 同時リクエストでも上限を越えないよう、AI実行前に枠を確保する。再送識別子で二重実行を防ぎ、自動リトライはしない。
- 利用回数を確認できない場合はAI検索を停止する。Supabase停止中も通常の端末記録や保存済み候補の閲覧は可能にする。
- 検索回数上限は厳密な金額上限ではない。提供元の利用制限も併用し、テストで検索ツール利用量を確認する。

## 保存設計

既存は `AppData` 全体を `app_snapshots` に保存する構造。旧端末が古い形式で保存してもアドオン情報を消さないよう、初回から保存先を分離する。

- `Favorite`: id、施設名、地域、ジャンル、出典URL、ユーザーメモ、検索日時、保存日時。workspaceIdはDBの別カラムで管理。出典種別は断定せず「参照サイト」に統一。
- 検索結果は原則ページ内の一時状態。保存ボタンを押したものだけ永続化する。
- Supabaseに `addon_outing_favorites` と `addon_ai_usage` を追加する小規模マイグレーション。既存テーブルの再設計はしない。
- 専用APIでお気に入りを行単位に追加・解除し、既存の全件スナップショット同期から独立させる。
- workspaceIdはサーバー設定から取得する。ブラウザ指定のworkspaceIdを信用しない。
- テーブルはRLS有効化、匿名・クライアントからの直接操作を許可せず、認証検証済みサーバー経由で操作する。
- 端末にはお気に入り一覧のキャッシュを別キーで保存。オフラインでは閲覧のみとし、未同期の変更キューは初回範囲外。
- 正規化したURL等で重複保存を抑制する。URLの追跡パラメータ除去は既知のものだけに限定する。
- 初回からアドオン用JSON出力・復元を提供する。既存の「全データ」バックアップUIには別保存である旨とアドオン出力への導線を明示する。

Service Worker v14では認証状態や利用上限を古いレスポンスで判断しないよう、APIをキャッシュ対象から外し、旧APIキャッシュも更新時に除去する。
汎用アドオン管理フレームワークや新しい状態管理ライブラリは不要。AI APIは既存のfetchによるREST呼び出しを優先する。

## 実装順と完了条件

0. UIイメージ画像を先に作成し、計画とともに共有。以降はその画像を参考に実装する。
1. 画像を基準に新規タブ・フォーム・カード・空状態を仮データで作成し、iPhone幅とPCで操作確認。
2. 検索アダプター・出典対応・入力検証・認証を実装。AI未設定時もアプリが起動することを確認。
3. 利用上限と専用保存APIを実装し、並行検索・二重送信・Supabase停止時を確認。
4. お気に入りと出力・復元、PWA更新を実装し、既存画面との回帰確認。
5. `npm run build` と主要ロジックの検査を実行。既存package.jsonには専用テストコマンドがないため、必要最小限の検証方法を選ぶ。
6. 実APIで少数の検索を行い、施設と出典の対応、料金区分、表示規約を確認してから公開。

受け入れ条件:

- 390px前後の画面で新規タブにアクセスでき、既存タブの操作を妨げない。
- 日常記録の保存・編集・クラウド同期が従来どおり動く。
- 地域と条件で検索でき、全候補に対応する出典URLがある。
- 犬同伴・大型犬・屋内など不明な条件を適合済みと表示しない。
- 未認証・機能停止・上限到達ではAI呼び出しが発生しない。
- 秘密キーが配信JS、ログ、Gitに含まれない。
- 保存・解除・重複抑制・再読み込み・共有・JSON復元が確認できる。
- 0件、タイムアウト、不正なAI応答、オフラインで再操作できる説明がある。
- 古いPWAから更新して新タブが表示され、APIエラーをキャッシュで成功扱いしない。

## 導入時の確認事項

AI提供元はOpenAI。検索込みの予算は提供元の利用状況で確認する。回数制限は家族共通で初期10回/日、実APIの検索品質・出典対応はキー設定後に確認する。
ユーザーにはAPIキーをチャットへ貼らず、Vercelのサーバー用Sensitive環境変数へ登録してもらう。
実装はユーザーの「すすめて」に基づく。契約・有料検索・DB適用は未実施。設定がない間、AI検索は実行しない。
